# Claude A/B GSB Console 需求说明

## 1. 建设目标

系统用于生产可提交的 Pair-wise GSB 数据。每个 Pair 在同一题面、同一 Git `main` 基线和相同 Claude 运行环境下，使用大写 `A`、`B` 两个分支、两个独立工作目录、两个容器、两个 Terminal 和两个 Session 完成一次开发，再保存双轨迹、双提交、双 Docker 验收、双录像和一份 GSB 对比结论。

系统与旧 Claude Eval Console 使用独立代码、数据库、项目目录和服务端口。旧系统只作为困难/地狱题目的可选只读来源。

## 2. 模型职责

- Claude 容器只负责 A/B 开发，默认模型为 `auto_model/urm`。
- Codex CLI 负责出题、难度与禁题复核、语义查重、基线检查、找 Bug、双次复现复核、GSB、公开理由复检和后续任务判断。
- Codex 默认模型为 `gpt-5.6-sol`。出题、准入和 GSB 使用 `medium`；找 Bug 使用 `high`；GSB 二次复检默认使用 `gpt-6-astra high`。
- 系统代码负责 Git、Docker、SQLite、轨迹导出、浏览器录像和提交文件校验，不能由模型虚构执行结果。

## 3. 题目规则

支持三类任务：0–1 代码生成、Feature 迭代、Bug 修复。

进入 A/B 开发的 0–1 和 Feature 任务必须为困难或地狱；从真实产物发现并双次复现的 Bug 修复允许中等、困难或地狱，简单 Bug 仍拒绝。困难任务需要整合多个模块或系统约束，并处理复杂状态、兼容性、权限、并发、性能或异常链路。地狱任务需要架构级判断、多步复杂调试或大量边界场景。文件多、页面多、字段多和题面长不能单独证明难度。

禁止生成或放行经典小游戏、图形模拟、通用命令行工具、本地文件工具、桌面小工具，以及电商、订单、RBAC、库存、OA、CMS、挂号、CRM、聊天、拍卖、停车、工单、预约、常见报表、记账、健身、菜谱、天气、番茄钟、习惯、播放器、旅行和观影记录等通用业务换皮题。

0–1 任务从空仓库开始。Feature 和 Bug 修复必须绑定真实来源项目、任务发生前的准确提交和项目链。Bug 候选必须在两次清洁 Docker 环境中复现成功，且难度至少为中等，才能转换为新任务。Bug 题面依据该候选的真实前置条件、操作、命令输出、源码位置、实际结果和正确行为单独生成，不使用固定开头、固定段落顺序或固定结尾；“前置条件／复现步骤／实际结果／预期结果”四段骨架及历史四种拼装句式均在入库前拦截。第一次生成不自然、套旧句式或与历史题重复时按原始证据完整重写，第二次仍不合格则停止该候选，不能回退到模板。

题目池低于配置水位时自动补题。生成结果仍要经过难度、禁题、语义查重和基线复核；不合格结果不能创建 Pair。

自动出题、自动调度和失败换题只使用通过准入的 0–1 题；Feature 与 Bug 修复继续保留在题库、历史记录和人工处理链路中，但不占用自动补位。任务进入 Pair 前再次检查重复标题和高相似题面，没有现成合格 0–1 题时直接生成新的困难或地狱 0–1 题。Feature 仍只能绑定真实完成项目的准确基线，Bug 修复仍只能来自真实产物并完成两次清洁环境复现，以便人工启用时保留完整证据链。

出题准入必须预演满足需求的最小正确实现，并读取 Feature/Bug 的准确基线源码和近期真实难度案例。若核心状态机、事务、算法、恢复或兼容机制已经存在，候选只是扩字段、加路由、增加条件分支、包装既有算法或补页面，应如实判为中等；Feature 中等候选拒绝，真实发现并双次复现的 Bug 修复中等候选允许进入。困难候选只选择一个贯穿主流程的真实主难点，可以是状态不变量、故障恢复、复杂跨层契约或具有独立判据的领域算法；开发者自行过度设计、叠加无关机制或增加测试数量不能用于抬高难度。

0–1 与 Feature 使用旧系统的范围预算。每道题只能有一个工程核心和一条用户主流程，涉及 3～4 个实现模块，最多 2 个新增接口或用户操作、1 组新增状态和 2 项辅助机制。0–1 最多 2 个应用运行组件，生成目标约 450 字并控制在 300～520 字，本地硬边界为 300～600 字，包含 3～6 个可观察验收场景；Feature 不增加独立运行组件，题面为 300～480 字并包含 3～4 个验收场景。两类题面均为一段 4～6 句的自然中文，单句不超过 120 字且分号不超过 2 个，按业务因果组织，不机械拼装数据库、接口、页面、测试、数值和通用交付清单。生成结果必须先通过结构化范围字段和本地规则复核，超出预算的候选不得进入题池。0–1、Feature 和 Bug 新题都不得要求项目仓库安装或运行 Playwright、Chromium、Puppeteer、Selenium、Cypress 等浏览器验收工具；Bug 的复现与验收只使用代码测试、构建检查、API/HTTP 冒烟或直接业务模块调用，页面功能统一由系统在仓库外操作和录像。

“语言/框架”只保存主要编程语言和主要应用框架，例如后端 `Python 3.13, FastAPI`、前端 `TypeScript, React`、全栈 `Python 3.13, FastAPI, TypeScript, React`。Pydantic、SQLAlchemy、Vite、数据库、测试工具、Playwright、Docker、用途、架构、算法、业务能力和限制条件均不进入该字段。新题生成、历史导入、导出和正式提交使用同一规范化结果。

题目池提供“一键自动运行完整流程”。启用后固定维持 3 个活动 Pair，优先消费现有已通过准入的题目；不足 3 个时自动创建和启动 Pair，没有可用题目时再自动补题。仓库准备、A/B 开发、Docker 验收、实际难度复评、浏览器录像和 GSB 默认确认均由调度器按状态继续执行，一个 Pair 完成或失败释放名额后自动补位。录像受单浏览器录制约束串行执行，不改变最多 3 个 Pair、6 个开发终端的硬上限。

首轮题面发出后 60 分钟仍没有业务代码时，系统记为一次 Pair 级失败并用新 Session 从共同基线重跑。第二次尝试达到 40 分钟时，若仍无代码且活动轨迹与上一次完全相同，可以提前停止重复空跑；轨迹不同则继续保留完整 60 分钟窗口。A/B 任一侧累计第二次失败后直接换下一道合格 0–1 题。

## 4. Pair 与 Git 规则

- 每个 Pair 创建一个独立 GitHub 仓库。
- 仓库必须只有共同起点 `main` 和大写 `A`、`B` 两个开发分支。
- A/B 在收到题面前必须指向同一个 `main` 提交，工作区保持清洁。
- 两侧使用完全相同的题面，每个有效 Session 只允许发送一次原题，不允许发送“继续”或其他追加消息。
- A/B 容器和工作区都准备完成后先向 A 发送题面，默认间隔 30 秒再向 B 发送；两侧的开发告警与终止时间分别从各自实际发送时刻计算。服务重启恢复和同时重跑也必须保持该间隔。
- 开发完成后分别提交并推送 A/B 分支，系统核验本地与远端 SHA 一致。
- Pair 并发与 Claude 开发终端并发独立配置。默认最多 3 个开发终端；Pair 的某一侧没有空位时保持排队，已有终端释放后自动启动。

## 5. 失败重跑

429、504、证书错误、连接错误等 Claude API Error 必须保留在原生轨迹和运行状态中，但出现时不得立即归档、重启或打断当前侧；该侧继续使用本轮从题面发送时刻开始的 60 分钟无业务代码时限，另一侧不受影响并可先完成验收。满 60 分钟仍无业务代码时才计为一次 Pair 级失败，从共同基线建立新 Session 并只发送一次数据库原题面，不向旧终端发送“继续”。A/B 合计第二次失败时只停止本次失败侧；另一侧继续运行到正常完成或触发自己的 60 分钟时限，之后再退役整个 Pair，并使用下一道合格 0–1 题补位。

作废后必须停止当前会话，导出并校验已有轨迹，从共同基线建立全新容器、工作区和 Session，再发送一次原题。不能在旧 Session 中继续。轨迹复制或校验失败时保留旧容器和工作区作为证据。

每个 Pair 最多容忍一次失败并重启失败侧一次。429、504、证书、连接错误和普通无代码超时都在本轮 60 分钟到期且仍无代码时计入同一个 Pair 级失败额度。A/B 合计第二次失败时停止达到失败上限的当前侧，但不连带停止另一侧。另一侧继续执行自己的 60 分钟无业务代码规则；待其完成或自然停止后退役整个 Pair，优先取已通过准入的 0–1 题，没有可用题时自动生成困难或地狱的 0–1 新题并创建替代 Pair。

## 6. Docker 验收与录像

每个 A/B 产物都必须包含 Dockerfile、Docker Compose、健康检查、可配置宿主机端口和执行完成后自行退出、以退出码报告结果的 `verify` 服务。新 0–1、Feature 与 Bug 题目的验收只要求代码测试、构建检查、API/HTTP 冒烟或直接业务模块调用，不要求项目仓库内的浏览器自动化。系统在独立项目名、随机空闲端口和清洁卷环境下执行 Compose 配置检查、构建启动、容器状态检查、`verify` 服务和清理。

录像只捕获独立 Chrome 的网页视口，不录桌面、终端、Dock、通知或其他窗口。输出为 H.264 MP4，分辨率固定 `1280×720`，时长必须大于 0 且小于 90 秒。自动录像的结束时间由真实操作完成时间加自然查看停顿决定，常规流程通常约 30–43 秒，并按每次录像变化，不能统一填充为固定时长。录像中必须显示页面内鼠标指针和点击圆点，并执行真实功能；Swagger 项目要完成 Try it out、有效参数、Execute 和成功响应，普通前端也要产生页面点击与成功的同源接口请求。

通过技术检查且与最终提交匹配的录像，按用户授权默认标记为审核通过。人工抽查不合格时可启动项目并人工重新录制；失败的重录不能覆盖当前合格录像，成功重录需要重新绑定提交证据并使旧 GSB 失效。

Feature 和 Bug 修复在 A/B 启动前必须先对共同基线执行一次清洁 Docker 预检。缺少 Dockerfile、Compose、Compose 配置无效或依赖路径错误时，题目在开发前被拒绝并自动补位；Docker 服务本身暂时不可用时保留 Pair 并重试，不能误判为题目缺陷。A 或 B 完成后立即单侧验收，结果按提交 SHA 复用。Claude 已经完成开发但原始交付缺少 Docker 文件，或无法清洁构建、启动、运行验收测试时，保留原提交和失败验收，不再启动 Claude 返修；系统录制 12–16 秒的浏览器终端画面，展示真实验收命令、输出和退出状态，再依据开发轨迹、代码与失败证据正常生成 GSB。失败录像只是故障证据，不得写成运行通过。两侧录像与 GSB 齐全后形成可提交数据。可以启动的产物仍必须先通过 Docker 验收，才进入难度复评和正常功能录像。

A/B 当前提交都通过后，系统必须在录像前根据真实交付重新评估难度。复评同时读取原题面、两侧代码差异、可见开发轨迹和 Docker 验收结果，分别记录 A 难度、B 难度、整体实际难度、理由和证据。文件数、步骤数、日志长度、环境安装或自行过度设计不能抬高难度；整体难度按完成需求所必需的真实复杂度判断。0–1 和 Feature 复评仍为困难或地狱才进入录像，Bug 修复复评为中等、困难或地狱即可进入录像；低于对应准入线时停止该 Pair、标记难度复评未通过并由自动流程补位。复评按 A/B 当前提交 SHA 幂等复用。已经完成或质检通过的历史数据不回写、不重新判定。

## 7. GSB 与复检

GSB 只能输出 `A better`、`Same` 或 `B better`。公开理由只保存“A 评价”和“B 评价”两段，选择依据自然融入两段，不单独生成偏好依据。每段在 Schema 允许的 20–300 个字符内把判断和证据说明白，不刻意追求最短，不含反引号、Markdown、JSON、模型名称或无证据结论。

GSB 必须依据当前 A/B 的真实轨迹写成口语化、连贯且证据充分的评价。可以保留多个存在因果关系的步骤、必要的测试数字、文件、函数和代码差异，但不机械罗列与结论无关的细节。步骤号必须来自原始 JSONL 记录，不能按总调用数猜测。已经修好的中间报错要连同恢复结果说明，不能写成最终缺陷；没有运行接口或业务测试时要直接说明，不能用编译通过代替业务验证。只有已复现且影响比较的 Bug 才写入公开评价，静态猜测或未复现候选不能当成事实。

复检以事实和逻辑正确为主：核对结论是否有证据支持、A/B 归因是否正确、开发过程与后续验收是否混淆、关键 Bug 或未验证范围是否遗漏，再检查表达是否口语化和易懂。不得仅因篇幅较长、数字或代码位置较多就要求精简；提出改写时必须保留所有会影响结论的有效证据。

复检必须区分证据充分与机械罗列。有因果关系的步骤、真实失败与恢复、影响结论的测试结果可以详细保留；连续测试用例编号、成组堆叠的测试数量，以及用录像秒数证明“没有功能缺陷”的写法应改成对应业务场景和客观结果。不得把这些内容简单删除后改成空泛的“验收通过、整体很好”。

GSB 生成和应用复检建议后，按用户授权默认标记为审核通过并进入待提交状态。页面仍保留搜索、分页、编辑、单条复检、批量复检、口语化和重新确认。“口语化”只能整理 A/B 理由的表达，必须锁定原结论并保留影响判断的事实和证据。高强度复检发现事实冲突时必须阻止正式提交；普通措辞建议可以由人工决定是否应用。

## 8. 提交与返修

“导出轮次”按 Pair 展示并筛选任务类型、系统类型、难度、资料、提交状态和完成日期，支持分页、批量复检、Excel 副本、隐藏与恢复。

Chrome 小助手必须动态读取 SOLO-QA 当前 `/api/v1/gsb/form-schema`，上传 A/B 两份 `.jsonl` 轨迹和两份录像，并提交题面、任务类型、难度、环境、SessionID、共同起点、两份产物、GSB 结论和两段理由。提交前必须核验：

- 两份轨迹的首条题面与本地题面逐字一致；
- A/B SessionID 不同，Harness 及版本符合本期要求；
- A/B 提交的父提交为共同 `main`；
- 轨迹和录像的文件大小、SHA256 与预检时一致；
- 远端表单没有本地无法映射的新增必填字段；
- 录像和 GSB 已确认，且没有未处理的事实冲突。

提交、返修和状态同步通过用户已登录的 SOLO-QA Chrome 页面执行。系统不能在用户未点击正式提交时自动上传外部平台。

## 9. 页面与统计

系统提供数据概览、题目池、A/B 项目、复核与人工确认、Codex 作业、Bug 复现、验收与录像、导出轮次和系统设置页面。

题目池显示自动运行开关、当前活动 Pair 数、目标数量、可用题目数和阶段分布；关闭自动运行后保留现有项目与证据，不强制终止正在执行的开发。

数据概览按 Pair 计数，一个 Pair 只算一条数据，并用颜色区分纯后端、纯前端和全栈，同时统计 0–1、Feature 与 Bug 修复任务。复核、验收和导出页面支持搜索、筛选、日期筛选及 20/50/100 分页，筛选和页码保存在 URL 中。

自动录像应依次操作页面中不重复且非删除类的可见功能控件，接口文档页连续演示多个业务接口，并保留真实点击、可见结果和成功请求证据。功能演示结束后立即保存录像，不为达到固定时长增加空等画面；人工重新录制仍由用户自行操作并主动停止。
自动点击要使用可见的分步鼠标移动，并在落点前和结果出现后保留略有变化的自然停顿；最后一个功能完成后固定展示结果 1 秒再保存，不得追加其他补时。

## 10. 数据、部署与验收

- 默认服务地址：`http://127.0.0.1:8865`。
- 数据库：`~/Library/Application Support/Claude A-B GSB Console/.data/pairwise.db`。
- 项目目录：`~/Library/Application Support/Claude A-B GSB Console/projects`。
- 运行副本：`~/Library/Application Support/Claude A-B GSB Console/app`。
- 用户配置：`~/Library/Application Support/Claude A-B GSB Console/config.env`，安装和升级不得覆盖。
- 服务以 macOS LaunchAgent 运行，登录后自动启动，代码升级前自动备份 SQLite。
- 所有路径必须基于当前用户的主目录，不得写死开发机器用户名或 Homebrew 安装位置。
- 交付前必须通过 Python 单元测试、JavaScript 语法检查、干净目录启动冒烟测试、服务健康检查和依赖预检。
